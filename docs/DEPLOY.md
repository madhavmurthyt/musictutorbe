# Deployment

The backend is deployed on **Render** as a web service.

## Render Configuration

Defined in `render.yaml`:

| Setting | Value |
|---------|-------|
| Service name | `naadaguru-api` |
| Runtime | Node.js |
| Plan | Free |
| Build command | `npm install` |
| Start command | `npm run db:migrate && npm start` |

Migrations run automatically on every deploy via the start command.

## Production Environment Variables

Set these in Render dashboard (not in `render.yaml` for secrets):

| Variable | Notes |
|----------|-------|
| `NODE_ENV` | `production` |
| `PORT` | `10000` (Render default) |
| `DATABASE_URL` | Render PostgreSQL connection string |
| `JWT_SECRET` | Auto-generated by Render |
| `JWT_EXPIRES_IN` | `7d` |
| `CORS_ORIGINS` | Comma-separated allowed origins (app scheme, web domains) |
| `GOOGLE_CLIENT_ID` | For verifying Google SSO tokens |
| `APPLE_CLIENT_ID` | For verifying Apple SSO tokens (bundle ID) |
| `FACEBOOK_APP_ID` | For verifying Facebook SSO tokens |

## CORS

`CORS_ORIGINS` must include the origins from which the app makes requests. In production, this is the app's custom scheme and any web domains serving the landing page.

## One-Time Scripts

### Conversation Backfill (Messaging Feature)

When the messaging feature was deployed, existing accepted inquiries did not have associated conversations. A one-time backfill script was run on the Render shell to create `conversations` rows for all enquiries with `status: 'accepted'` that lacked a conversation.

This only needs to be re-run if conversations are manually deleted or if the messaging feature is deployed to a new environment with existing accepted inquiries.
